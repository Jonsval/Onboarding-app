Convenciones de Código, Flujo Git y Comunicación

Tamaño:

Bienvenido al módulo de estándares de trabajo. En esta guía documentamos las directrices que permiten a nuestros equipos multidisciplinarios entregar valor de manera predecible, segura y con alta calidad de software.

💡 Principio Clave: La consistencia en nuestros estándares reduce la fricción técnica y permite que cualquier miembro del equipo pueda entender y colaborar en cualquier módulo del proyecto.

1. Convención de Ramas en Git

La rama main contiene el código que se encuentra actualmente en producción o listo para despliegue inmediato. Ningún desarrollador puede realizar push directo a main.

Formato estándar de ramas:

feature/[TICKET-ID]-descripcion-corta # Nuevas funcionalidades fix/[TICKET-ID]-descripcion-del-bug # Corrección de errores docs/[TICKET-ID]-tema-documentado # Mejoras en documentación refactor/[TICKET-ID]-modulo-optimizado # Refactorizaciones sin cambio de comportamiento

Ejemplo práctico: feature/DES-142-onboarding-form

2. Formato de Commits Semánticos

Seguimos la especificación de Conventional Commits para facilitar la generación automática de changelogs y versionado semántico.

feat(auth): agregar autenticación por SSO con Azure AD fix(perfil): resolver error de carga en avatar de usuario docs(readme): actualizar instrucciones de instalación local

3. Buenas Prácticas en Pull Requests

Antes de solicitar la revisión de tu código, asegúrate de cumplir con la siguiente lista de verificación:

Checklist obligatorio de PR:
  • El tamaño del PR no supera las 400 líneas modificadas (salvo dependencias generadas).
  • Pasan todas las pruebas unitarias y linters automáticos en el CI.
  • Se incluye descripción del cambio y captura de pantalla si incluye cambios visuales.
  • Cuenta con al menos una aprobación (LGTM) de un revisor asignado.

4. Gestión de Tareas en Jira

Cada tarea debe reflejar su estado en tiempo real. Cuando comiences a trabajar, muévela a In Progress. Al crear el Pull Request, muévela a In Review.
